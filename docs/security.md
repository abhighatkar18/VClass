# Security and release readiness

## Current controls and outstanding verification

| Area | Implemented control | Release follow-up |
|---|---|---|
| Authentication and profile | Firebase Authentication owns passwords. New Firestore documents contain only name and email at creation. Repository rules prevent introducing password-derived fields and restrict profile access. | Verify Email/Password, reset, session restoration, and sign-out in staging. Inventory any historical password-derived fields. Cleanup requires an approved migration and backup plan. |
| Classroom, roster, and assignments | Firestore rules enforce membership and role access. Roster records expose display names. An assignment author can list its submissions. Stable IDs preserve same-title and historical assignment paths. | An authorized maintainer can open **Firestore Database → Rules** in each Firebase console, compare them to [firestore.rules](../firestore.rules), record any differences, and run the role checks in staging. Review historical assignment records before proposing any migration. |
| Gemini | Local development reads the key from ignored `local.properties`. CI leaves the key empty. | A key supplied at build time is embedded in `BuildConfig` and may be recovered from the APK. Before distribution, move credential use to an authenticated, rate-limited server. Review and rotate any live key that was distributed. [Gemini key guidance](https://ai.google.dev/gemini-api/docs/api-key) |
| Cloudinary | Client uses a cloud name, an unsigned preset, streamed uploads, and saved HTTPS links. | Confirm upload limits, allowed formats, abuse protections, and asset access controls. A Firestore rule limits access to stored URLs. A copied publicly accessible URL can bypass that application check. Review signed uploads and restricted asset delivery before sensitive use. [Cloudinary upload presets](https://cloudinary.com/documentation/upload_presets) |
| Dependencies | Debug lint runs in CI. | Investigate the transitive Google HTTP Client's TLS lint warnings and whether the flagged code is reachable. Verify Realm's native alignment on Arm64 16 KB devices. Review the test CLI's transitive dependencies separately from the APK. |
| Repository and Actions | Local settings, variant-specific Firebase overrides, service-account patterns, signing files, and generated outputs are ignored. CI uses a fake Firebase fixture, read-only repository permissions, pinned actions, and report artifacts. | Preserve secret-scanning and PR checks where supported by repository settings. No GitHub secrets are required for the implemented jobs. Restrict secrets to a future trusted release environment if approved. |

The tracked base `app/google-services.json` contains Firebase Android client identifiers. Firebase generally treats those client API keys as project identifiers. Check key restrictions and service authorization separately. Service-account keys and Gemini keys are private. The local history check looked for known secret file paths and common key signatures without printing their contents. Treat it as a targeted review. Adding an ignore rule only affects untracked files and leaves existing Git history intact. If a private key is discovered, restrict and rotate it, then scope history cleanup with the repository owner. [Firebase API key guidance](https://firebase.google.com/docs/projects/api-keys)

## Release checklist

- Confirm the staging walkthrough, deployed rules, credential handling, and file access controls. Verify a supported physical device and an Arm64 16 KB environment before making compatibility claims.
- Review SDK and distribution requirements when planning a release. The current app declares version code **1**, version name **1.0**, target SDK **35**, and release minification disabled.
- After release configuration is approved, run `:app:lintRelease` and an appropriate release build. Android Studio's **Generate Signed Bundle / APK** supports signed APK and AAB generation. A future protected build can use `:app:assembleRelease` or `:app:bundleRelease` with approved signing inputs. Keep signing material outside the repository.
- If R8 or resource shrinking is enabled, test Firebase, Compose, Gemini, Realm-related code, file handling, and reflection on the actual artifact. Check version and package identity, signature, installability, and behavior using an authorized test device. Review the artifact for embedded credentials before distribution.
- The current GitHub workflow verifies debug builds and retains test and lint logs. Publication, release signing, deployment, and Play Store upload require separate approval.
